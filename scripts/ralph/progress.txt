## Codebase Patterns
- Stage 20 batch accept orchestration lives in `src/batch_engine/controllers/batch_accept_controller.py`: `accept_batch_items(batch_id, items, load_request, accept_one, item_ids=None, queue=None)` accepts selected (item_ids filter, batch order preserved) or all items, reuses the existing Request accept capability via injected `load_request`/`accept_one` callables (Web layer wires `accept_one` to `apply_confirmation_action` + `_build_history_event` + `apply_request_save_action`), returns `already_accepted` idempotently for ACCEPTED requests (no history/queue re-write), returns per-item Chinese reasons for unacceptable items (missing request_id/snapshot, CANCELLED, other status), enqueues each successful accept as READY_TO_SUBMIT, and never lets one item's failure block the rest. Queue titles are defensively sanitized with `sanitize_queue_summary`; serialize via `serialize_batch_accept_result`.
- Stage 20 batch pre-submission queue lives in `src/batch_engine`: models in `batch_engine/models/queue.py` (`BatchQueueItem`/`BatchSubmissionQueue`, statuses READY_TO_SUBMIT/SUBMITTING/SUCCEEDED/FAILED/RETRYABLE, Chinese `BATCH_QUEUE_STATUS_LABELS`, `BATCH_QUEUE_TRANSITIONS`), controller in `batch_engine/controllers/batch_queue_controller.py` (idempotent `enqueue_item` keyed by `request_id`, `start_queue_item_submit` increments `attempts`, `complete_queue_item_submit`, `mark_queue_item_failed`, `sanitize_queue_summary`, safe `serialize_queue`/`serialize_queue_item`). The queue never stores Auto Bangumi secrets (endpoint/token/cookie/Authorization/raw response body/full RSS URL/magnet) — summaries are sanitized on write and re-sanitized defensively on serialization. `mark_queue_item_failed` is restricted to READY items (pre-submit validation); SUBMITTING items must finish via `complete_queue_item_submit`.
- Stage 20 batch Auto Bangumi sequential submit orchestration lives in `src/batch_engine/controllers/batch_submit_controller.py`: `submit_batch_queue_items(batch_id, queue, ab_config, load_request, submit_one, now_factory=None)` processes READY_TO_SUBMIT items in queue order — already-SUCCEEDED and non-READY items are SKIPPED without any submit call, then each READY item is pre-submit validated against the current Request snapshot via the injected `load_request` (missing/deleted → FAILED `request_not_found`, CANCELLED → FAILED `request_cancelled`, any other non-ACCEPTED → RETRYABLE `invalid_request_status`), moved to SUBMITTING via `start_queue_item_submit` (increments attempts), submitted through the injected `submit_one(request, ab_config)` that returns the existing sanitized `ab_submit_result` contract, and finalized via `complete_queue_item_submit` (SUCCEEDED stores a sanitized `ab_result_summary`; FAILED/RETRYABLE store a sanitized `last_error`). Transient AB errors (`ab_timeout`, `ab_connection_failed`) map to RETRYABLE, all other submit errors map to FAILED, and one item's failure never blocks the rest. `compose_ab_submit_one()` builds the standard submit_one from `build_ab_subscription_payload` + `create_auto_bangumi_http_client(ab_config)` + `submit_ab_subscription` — the batch-domain equivalent of `apply_ab_submit_action`'s AB portion — so the Web layer can wire the real path without reimplementing payload/client logic. The queue never stores the request-scoped ab_config.
- Stage 20 batch queue persistence lives in `src/storage_engine/controllers/queue_repository.py`: `save_submission_queue(config, queue)` writes `<queue_dir>/<batch_id>.json` (round-trip storage dicts from `batch_queue_controller.queue_to_storage_dict` / `queue_item_to_storage_dict`, reconstructed by `queue_from_storage_dict` / `queue_item_from_storage_dict`), and `load_submission_queue(config, batch_id)` raises a stable Chinese `queue_not_found` when absent, `invalid_batch_id` for traversal/empty ids, and `storage_json_error` for damaged JSON. `queue_dir` is a new `StorageConfig` field (`storage_config.py`) created by `ensure_storage_layout`. Round-trip storage serialization is intentionally distinct from the public `serialize_queue` boundary: the persisted queue holds only non-sensitive fields (summaries sanitized on write), so the API never stores Auto Bangumi secrets.
