- **Learnings for future iterations:**
  - Patterns discovered
    - TrackingRecord 模型 = 内容契约（无持久化依赖）；repository 按仓库惯例放 `storage_engine/controllers`
      并 import `tracking_engine.models`（与 queue_repository → batch_engine.models 同构）。
    - CAS 的 revision 语义：repository 负责「加载当前 → 校验 base → 校验 next.revision == base+1 → 原子写」；
      状态/审计/revision 在同一记录内原子落盘。US-224+ 的 revalidate/submit/retry/recover 服务只构造
      `transition_record` 结果再 CAS，不要在路由层复制 revision 逻辑。
    - fail-closed 分两层：模型层 `tracking_from_storage_dict` 抛 `ValueError`（unknown 顶层字段/schema 版本/
      状态/origin/类型）；repository 层把 `ValueError` 映射为稳定 `storage_json_error`。list 对损坏文件吞
      Stage1Error 并只报告 opaque damaged ids。
    - 新增存储族三处必改：`storage_config.py` 的 dataclass + `load_storage_config` +
      `ensure_storage_layout` 目录元组，再同步 `storage_config_test.py` 与 hatch `packages`（若是新 engine）。
  - Gotchas encountered
    - compare-and-swap 的校验顺序：必须先 load 当前记录（missing → `tracking_not_found`）再校验
      next record 的 revision 不变量，否则对不存在记录做 CAS 会误报 `invalid_tracking_record`。
    - `uv run pytest` 自动重建 editable wheel；新增顶层 `tracking_engine` 后 `pyproject.toml` packages
      未更新会导致 import 失败——先加 package 再跑测试。
    - ruff 会自动重排 import；`tracking.py`/`models/__init__.py`/测试文件在首次 `ruff --fix` 后被改写，
      提交前以 `ruff check src tests` + 定向 pytest 为准。
    - `_LAST_ERROR_FIELDS` 用 tuple（不是 frozenset）保证 last_error JSON 键序确定；frozenset 迭代顺序跨
      进程不稳定。
