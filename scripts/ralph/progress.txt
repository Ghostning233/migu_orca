## Codebase Patterns
- Stage 1 through Stage 6 are complete; archived Ralph records live under `scripts/ralph/archive/`.
- Stage 7 Ralph work uses branch `agent/stage7-flask-web-ui` and should complete one `passes=false` story per iteration.
- Use `uv run pytest` and `uv run python -m compileall -q src` for project quality checks; bare `pytest`/`python` may not be on PATH.
- Preserve the existing top-level CLI JSON result envelope and do not change the current `migu-orca` command behavior while adding Web UI support.
- Default CLI and Web UI Request generation must remain offline and fixture-backed unless the user explicitly opts into real external integrations.
- Default generation must not write local storage unless the caller explicitly opts into persistence through `--save-request` or the Web API `save_request=true` contract.
- Stage 6 storage layout is centralized in `storage_engine.controllers.storage_config`; use `load_storage_config(...)` and `ensure_storage_layout(...)` instead of duplicating path conventions.
- Request persistence lives in `storage_engine.controllers.request_repository`; save/load complete Request dictionaries by `request_id` and keep error details to stable IDs, directory names, and filenames rather than absolute paths.
- Status history persistence lives in `storage_engine.controllers.history_repository`; append separate per-request JSON arrays under `history/` and keep transition metadata out of the saved Request snapshot contract.
- AB submit result persistence lives in `storage_engine.controllers.ab_result_repository`; write separate per-request JSON records under `ab_results/` only when `request.ab_submit_result` is an object from explicit AB submit behavior.
- Existing Request summaries are produced by `request_engine.controllers.request_controller.summarize_request(...)`; API/list views should reuse that contract where possible.
- Real external adapters should live behind engine-specific client/transport seams, with tests using injected fake transports instead of live network access.
- Do not include raw HTML, raw RSS XML, complete endpoint URLs, cookies, tokens, absolute local paths, or other sensitive config values in structured error details, logs, persisted errors, fixtures, API responses, UI text, or documentation examples.
- Stage 7 Flask Web UI must reference `/home/ghostning/github/user_level_flask` for structure: `src/apps/base.py:create_app`, `src/apps/registry.py:ALL_BLUEPRINTS`, module Blueprints, `extensions/flask_api` style response helpers, class-based `GetView`/`PostView`, Pydantic validators, `src/wsgi.py`, and Flask test client coverage.
- Stage 7 Flask blueprints should be exposed as per-module `blueprints` lists and registered centrally through `apps.registry.ALL_BLUEPRINTS`.
- Health endpoints still return the target JSON envelope directly: `{ok: true, result: "ok"}`; API blueprints added after US-048 should use `extensions.flask_api`.
- Stage 7 unified API helpers live in `extensions.flask_api`; use `ok_response(...)`, `failed_response(...)`, `route(...)`, `class_route(...)`, `GetView`, and `PostView` for JSON APIs.
- `extensions.flask_api` converts `Stage1Error`, `APIException`, and Pydantic `ValidationError` into the shared response envelope; unexpected exceptions re-raise under testing/debug and become generic `internal_server_error` responses otherwise.
- API error responses must pass through the extension sanitizer before exposing details; it redacts absolute paths, URLs, token-like keys/strings, and raw HTML/RSS content.
- Keep Stage 7 as a Flask server-rendered Web UI MVP with minimal JavaScript; do not introduce React/Vite or a separate frontend build unless explicitly approved.
- Stage 7 canonical Web UI homepage is `/index`; root `/` should redirect to `/index`.
- Stage 7 is a minimum viable Web UI and should not implement confirm/cancel/modify actions unless explicitly re-scoped.
- Stage 7 Web API may accept `storage_dir` from query/body for local validation convenience; keep errors sanitized and avoid leaking absolute paths.
- MiKan search and real-page RSS compatibility follow-up is tracked in `docs/backlog.md` and should not block Stage 7 Web UI work unless explicitly pulled into scope.
