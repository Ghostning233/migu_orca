# MiGuOrca Ralph Progress - Stage 29

## Codebase Patterns

- 本阶段只实现 B-B：TrackingRecord/TrackingOperation repository、纯本地历史迁移、accept/save-confirm
  接入 handoff、tracking 列表/详情、revalidate、统一 submit/retry/recover 与旧入口兼容；
  不实现 Auto Bangumi 全量管理、外部同步或新页面视觉（B-C）。
- Web API 路由按 `routes_*.py` 注册；请求模型在 `schemas.py`，响应 DTO 在 `api_contract.py`，
  serializer 负责公开白名单，service 编排现有 engine/repository。
- 新增/修改 `/api/v1` 端点必须同步 endpoint inventory、`openapi_gen.py`、`openapi.json`、
  生成 TypeScript client 和契约测试；operationId 必须显式、可读、稳定。
- envelope 和 HTTP 分类继续使用 Stage 26 统一实现；错误不得包含 draft、原始 payload、完整 URL、
  magnet、凭据、上游响应、堆栈或本地绝对路径。
- Web `storage_dir` 只能是服务端根下的相对 profile；空值必须回落服务端 Web root，测试使用临时根。
- `draft_id`、revision、idempotency key、tracking_id 只存在请求体和页面内存，不进入 URL 或 browser storage。
- Python 使用 `uv`，前端使用 `npm ci`；自动化通过 fixture/fake transport，禁止访问真实外部服务。
- 每次迭代只完成最高优先级的一个未通过 story；完整实现、测试和提交后才把 `passes` 改为 true。
- 分层门禁（Stage 29 PRD §17.2）：US-219～US-226 只跑受影响定向测试 + ruff + compileall + git diff --check；
  仅改 API contract 的 story 跑 OpenAPI 生成/检查和前端生成客户端测试；纯后端 story 不重复跑完整前端/浏览器；
  US-227 才跑一次完整非浏览器 + 前端 + OpenAPI drift + Chromium。
- Stage 28 已建立：服务端权威 DraftStore（revision/CAS/reserve/commit/release/peek）、save-confirm 幂等
  repository（`<storage>/idempotency/`）、单番/批量 save-confirm 端点、Request safe-info 白名单。Stage 29
  复用这些能力：tracking ensure 从 ACCEPTED Request + save-confirm handoff 建立 record；TrackingOperation
  是独立 repository，不扩展 save-confirm 幂等 repository（D29-04）。
- Stage 29 新增 `tracking_engine` engine（US-219）：TrackingRecord 模型、状态/状态组/审计模型、确定性
  `tracking_id_for_request` 在 `tracking_engine/models/tracking.py`；持久化 repository 按仓库惯例放在
  `storage_engine/controllers/tracking_repository.py`（repository 导入 tracking_engine 模型，类似
  queue_repository 导入 batch_engine.models）。`StorageConfig` 目录族新增
  `tracking/tracking_operations/tracking_migrations`，新增存储族必须同步 `storage_config.py` +
  `storage_config_test.py`；新 engine 需加入 `pyproject.toml` 的 hatch wheel `packages`。
- TrackingRecord repository（US-219）模式：`ensure`（create-if-absent，keyed by 确定性 ID，绝不覆盖已有）、
  `load`、`compare_and_swap`（revision 精确 +1，冲突抛 `tracking_revision_conflict`）、`list`（健康记录 +
  damaged opaque ids，损坏文件不阻塞不删除）。写用 temp + `os.replace` 原子替换；进程内按 tracking_id RLock
  串行并发 ensure/CAS（多 worker 共享 storage 仍不支持）。schema 校验在模型层抛 `ValueError`，repository
  映射为稳定 `storage_json_error`/`invalid_tracking_record`/`invalid_tracking_id`，绝不泄露路径/原始字节。
- TrackingOperation repository（US-220）模式：`operation_id` = `op_` + 版本命名空间
  `migu-orca/tracking-operation/v1\x00` + idempotency_key 的 sha256 前 32 hex（key 永不成为文件名）。
  `bind_tracking_operation` 同键同绑定重放、异绑定抛 `tracking_idempotency_conflict`；CAS 用 on-disk
  state == expected_state 做乐观并发，禁止改写 immutable 绑定字段。模型提供
  `transition_tracking_operation` 构造 next op，服务层不得在 route 复制状态机。
- US-221 迁移：manifest 固定存 `<storage>/tracking_migrations/schema-v1.json`（模型严格白名单 + repository
  temp/os.replace 原子写）；COMPLETE 后不再全量扫描，PARTIAL 会重试；manifest 只保存时间窗与安全计数。
- US-221 纯分类在 `tracking_engine/controllers/migration.py`（无 storage import），协调器放
  `apps/migu_orca_web/tracking_migration_service.py`；扫描对损坏源文件用 storage repository 的
  damage-aware list（健康项 + 损坏 opaque id），单条损坏不阻塞健康清单，绝不暴露文件名/路径/原始 JSON。
- 迁移审计 = `TRACKING_BACKFILLED` + actor `MIGRATION`；record 保持 revision=1，一致多来源追加审计不 bump
  revision；ensure 收敛同一确定性 tracking_id，重复运行不新增记录/不重复审计。
