# MiGuOrca Ralph Progress - Stage 29

## Codebase Patterns

- 本阶段只实现 B-B：TrackingRecord/TrackingOperation repository、纯本地历史迁移、accept/save-confirm
  接入 handoff、tracking 列表/详情、revalidate、统一 submit/retry/recover 与旧入口兼容；
  不实现 Auto Bangumi 全量管理、外部同步或新页面视觉（B-C）。
- Web API 路由按 `routes_*.py` 注册；请求模型在 `schemas.py`，响应 DTO 在 `api_contract.py`，
  serializer 负责公开白名单，service 编排现有 engine/repository。
- 新增/修改 `/api/v1` 端点必须同步 endpoint inventory、`openapi_gen.py`、`openapi.json`、
  生成 TypeScript client 和契约测试；operationId 必须显式、可读、稳定。
- envelope 和 HTTP 分类继续使用 Stage 26 统一实现；错误不得包含 draft、原始 payload、完整 URL、
  magnet、凭据、上游响应、堆栈或本地绝对路径。
- Web `storage_dir` 只能是服务端根下的相对 profile；空值必须回落服务端 Web root，测试使用临时根。
- `draft_id`、revision、idempotency key、tracking_id 只存在请求体和页面内存，不进入 URL 或 browser storage。
- Python 使用 `uv`，前端使用 `npm ci`；自动化通过 fixture/fake transport，禁止访问真实外部服务。
- 每次迭代只完成最高优先级的一个未通过 story；完整实现、测试和提交后才把 `passes` 改为 true。
- 分层门禁（Stage 29 PRD §17.2）：US-219～US-226 只跑受影响定向测试 + ruff + compileall + git diff --check；
  仅改 API contract 的 story 跑 OpenAPI 生成/检查和前端生成客户端测试；纯后端 story 不重复跑完整前端/浏览器；
  US-227 才跑一次完整非浏览器 + 前端 + OpenAPI drift + Chromium。
- Stage 28 已建立：服务端权威 DraftStore（revision/CAS/reserve/commit/release/peek）、save-confirm 幂等
  repository（`<storage>/idempotency/`）、单番/批量 save-confirm 端点、Request safe-info 白名单。Stage 29
  复用这些能力：tracking ensure 从 ACCEPTED Request + save-confirm handoff 建立 record；TrackingOperation
