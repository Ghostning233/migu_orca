# 批量外部写的边界

「我的追番」的批量能力从「仅批量提交」扩展为三种动作：提交、删除本地记录、删除本地记录并同时删除受控外部订阅。批量外部写打破了 Stage 38 的单飞不变量，并可能一次制造多条未决结果，因此需要把允许的范围与执行约束一次写死。

## 决策

1. **允许的批量动作只有三种。** 批量提交（已有 `submitTrackingBatch`）、批量删除本地记录、批量删除本地记录并同时删除受控外部订阅。后两者需要各自的显式批量契约，不接受前端循环调用单条端点。
2. **明确不允许的批量动作：启停、修改、刷新 RSS、重新提交、单独删除外部对象。** 启停经过评估被否决——它的收益不足以覆盖"一次操作乘法产生多条未决结果"的成本；单独删除外部对象这个单条动作本身已在 #218 讨论中退役。要新增任何批量外部写动作，必须重新评估本决策。
3. **顺序执行，且必须有明确的互斥范围。** 批内顺序执行**不等于**系统级单飞：还必须定义一整个批次与其它批次、以及批次与单条外部写之间的互斥规则，否则两个批次可以同时对同一批对象发起外部写。
4. **执行时逐条重验资格，不是只在下单时校验。** 一个条目在用户勾选时可能可删，轮到它执行时可能已进入未决。因此每条执行前必须在服务端重验状态、revision、当前 operation 与批量资格；**新变成未决的条目跳过并返回原因，绝不自动转换为「放弃跟踪」**——放弃跟踪是单条的、需要独立风险确认的动作（见 [ADR-0006](0006-abandon-unresolved-tracking.md)），不能被批量路径静默借用。
5. **逐条结果，部分失败不阻塞其余条目。** 批量响应必须逐条给出结果与原因；单个条目的外部删除失败或结果未知时，该条目不删除任何本地数据，其余条目照常处理。不提供「全部重试」，失败项只能单独处理。
6. **批次自身必须具备幂等与超时语义。** 调用超时或连接中断后，必须能判定该批次是否已执行、如何查询结果、以及是否可用同一幂等键重放；不得让用户面对一个"不知道跑没跑"的批次。
7. **批量确认必须写明作用范围。** 确认弹窗以「仅删除本地记录」为默认范围，另以勾选框决定是否同时删除受控外部订阅，并说明将影响的条目数与跳过原因（例如未决条目、不适用条目）。

## 后果

- 批量操作整体是独立工作包，不属于「我的追番页信息架构」的视觉改造范围：它的主体是新后端契约与外部写边界。
- 「我的追番」的批量工具栏因此只有一个外部写动作组（删除时勾选外部）加一个已有的批量提交，不再扩张。

## 修订（#248）：批次互斥按资源分层

原决策 3 的「批次期间所有单条写互斥」在实测中把纯本地核验与无关 profile 一并拒绝，且入口拒绝发生在请求解析之前。修订后的粒度：

- 批次租约发布占用的资源域：storage profile + `tracking_id` 集合（+ 指定连接时的 connection generation）。
- 请求入口只提前拒绝「同 profile、批次占用的记录」上的**外部写**七条路由；纯本地/只读核验（`check`/`revalidate`/`recover`）、无关记录、其它 profile 不再被拒。非法 JSON/非法 profile 交给视图返回 400。
- 最终冲突检查与批次占用共用同一把 store 锁与同一谓词（`batch_conflicts_with`），无批次时外部写意图持锁跨越 bind+指针+门，批次不能中途启动。
- 批次指定连接时，替换/删除该 AB 连接（settings `PUT|DELETE`）在批次期间返回 409；未指定连接的纯本地批次不阻止连接变更。
- 批次↔批次、批次幂等、顺序执行、外部删除语义均不变。
