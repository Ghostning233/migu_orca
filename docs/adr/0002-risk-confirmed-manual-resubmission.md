# 主动重发不是原请求的安全重试

Auto Bangumi 3.1.18 既不返回逐条 torrent 的添加结果，也不提供可查询的幂等操作标识（见 [ADR-0001](0001-at-least-once-existing-resource-submission.md)）。因此「结果待确认」的持续追番提交永远不能被当作「确定失败」：MiGuOrca 既不能断言外部订阅已经建立，也不能断言它没有建立。ADR-0001 的「下载现有资源」至少一次语义保持不变，本决策只覆盖**持续追番**待确认结果的单条人工重发。

## 决策

1. **主动重发 = 用户承担风险的新操作，不是原请求的安全重试。** 它不复用、不重放、不修改也不删除原来的待确认 `TrackingOperation`，而是以新的幂等键创建一个新的 operation，并记录 `previous_operation_id` 指向原 operation。原未决记录、状态与审计事件全部保留。
2. **先只读检查，再谈重发。** 点击「重新提交」的第一阶段只执行与 #183 相同的、绑定原 operation 所连接实例的有界只读检查：
   - 已证实订阅存在 → 记录收敛为「正在追番」，**外部写入为零**；
   - 仍无法证实 → 返回已证实的原因分类与绑定信息，**不自动重发**。检查失败（认证/版本/能力/连接不可用）不构成重发授权。
3. **风险确认必须绑定精确上下文。** 第二阶段（`confirm=true`）必须携带第一阶段发布的 `expected_revision`、原 `previous_operation_id` 与连接 generation；任一变化即拒绝该过期确认（409），绝不改绑到另一条 operation 或另一个 Auto Bangumi 实例/连接代际。
4. **一次确认至多一个新 operation、至多一次提交调用。** 新 operation 的幂等键由服务端从上述绑定推导，因此同一次确认的重放或并发请求收敛到同一个 operation；只有赢得 `PREPARED → IN_PROGRESS` CAS 的调用方会接触 Auto Bangumi。
5. **保护不得绕过。** 外部写可能仍在执行（原 operation 仍为 `IN_PROGRESS`）、连接或无版本能力被证实无效、本地方案不满足提交前提（含方案已变化）时，一律禁止重发，并向按钮返回已证实的原因；不提供批量强制重发。

## 后果

- 「重新提交」在 UI 上是两步：只读检查 → 明确的风险确认（固定中文文案来自服务端的 `verification_reason`）。取消不产生任何外部写入。
- 待确认记录因此有两种不同的下一步：只读「重新检查」（ADR-0001/#183 路径）与用户承担风险的「重新提交」（本 ADR）。两者都不会把未决结果改写成「提交失败」。
- 由于上游没有幂等标识，重发后仍可能出现重复订阅或重复资源处理；文案必须如实说明，不得承诺安全重试，也不得声称 MiGuOrca 已去重。
