本任务将“添加番剧”页的六个指定状态复刻到固定参考画布：单番搜索、单番候选加载、单番草案审核、批量搜索加载、批量候选加载、批量草案审核。此前 Stage 40～45 的目标是方向、信息层级与业务体验；其 PRD 明确不做逐像素验收。本 PRD 是后续独立视觉工作，不能以历史视觉完成记录取代本次验收。

“像素级”只适用于以下可重复条件：项目固定的 Linux Chromium、100% 缩放、`1440×900` viewport、固定中文脱敏 fixture、本地确定性图片/占位资源、字体加载完成、关闭浏览器扩展并稳定动画后截图。六张图的生成说明明确以 `1440×900` 为目标；文件实际为 `1586×992`，两者宽高比近似但像素网格不同，实施时必须按同一确定性算法把不可变源图归一化到标准桌面基线，不能把位图物理尺寸误写成 CSS viewport。

真实搜索结果的标题长度、候选数量、封面、错误文本和用户缩放会变化，按本 PRD 的响应式/可访问性 AC 验收，不要求复制虚构内容或生成图瑕疵。像素验收采用“稳定视觉区域图像差异 + 关键锚点几何 + computed style”三层证据，不用单一整页相似度掩盖错位。

### 现状核对结论

- 当前应用已具备六图所需的主旅程、服务端草案权威、候选就地加载、批量左卡右详情、两种本地确认范围和未知结果恢复；本任务不能重写这些能力。
- 当前 `App.vue` 与 `WorkbenchView.vue` / `BatchWorkbenchView.vue` 的 DOM 层级、标题区、面板和工具栏仍以通用工作台为主；`AnimeDraftEditor.vue` 的摘要为字段网格和技术折叠，和图 03/06 的卡片式身份、双栏资源区并非同一视觉骨架。因此不能只调几个 token 宣称完成。
- 设计图中包含虚构封面、状态和文字。实现只能使用已有公开候选的安全封面代理；没有来源时用确定性占位，不伪造季度、集数、资源数或“已更新集数”。
- 当前 Python Playwright 测试只能生成截图，仓库没有 PNG 解码/像素比较依赖或既有 golden-screenshot 框架。Stage 46 必须先增加最小的测试期比较能力并更新锁文件，不能把人工目测写成自动化已通过。

### 规格优先级

发生冲突时依次采用：安全/业务状态机和无障碍硬约束 → 现行交互规格与 Design Token V1 的明确数值 → 六图归一化后的布局、密度和状态表达 → 图中的示例文案、虚构封面和生成瑕疵。当前用户要求将六图提升为像素级布局验收依据，但不推翻秘密边界、真实数据来源、最小点击尺寸、对比度和键盘行为。

## 2. 不可改变的产品与安全边界

- 用户仍必须手动选择真实 MiKan 合集；唯一候选不得自动选择，`CONFLICT`/季度证据确认规则不放宽。
- 草案仍以服务端 `draft_id + revision` 为权威；保留 CAS、scheduler、1.5 秒筛选防抖、flush、原子 save-confirm 和 unknown 冻结恢复。
- “保存修改”只更新本次草案；“保存并确认”只保存本地方案；提交到 Auto Bangumi 仍在追番管理另行明确确认。
- 批量中“查看”只切换右栏，“勾选待确认”只改变集合；N 部和确认全部的现有 D-02/D-04 语义、冻结 body/key/revision/item_ids 不得改变。
- 不新增 API、OpenAPI 字段、后端、存储、外部写、单条批量重搜、伪实时进度或未保存 safe-info；不把 RSS URL、magnet、Cookie、秘密、原始响应、绝对路径或完整 Request 放入视觉 fixture、DOM、截图、trace、URL 或浏览器存储。

## 3. 视觉规格与验收方法

### 3.1 共同视觉规格

1. 壳层按图使用白色顶栏、左侧品牌、四项一级导航、珊瑚红激活文字/下划线、右侧轻量连接胶囊；现有可访问名称、路由和连接状态语义保留。
2. 主色以深海军蓝、珊瑚红、浅蓝灰画布为准；字体权重、圆角、阴影、描边、控件高度和间距均从一次测量得出的 token 消费，禁止在页面散落“魔法数”。
3. 图 01/04 的首页是居中英雄区；图 02 是候选卡片比较区；图 03 是居中审核容器；图 05/06 是全宽批量双栏与底部操作区。页面状态切换不得产生无关空态或布局跳变。
4. 设计图里的图标必须来自可访问的本地 SVG/现有组件或纯 CSS，不引入未经许可的在线字体、图标或图片请求；装饰性图标 `aria-hidden`，操作保留文字和可见焦点。

### 3.2 可执行的像素验收

每个基准状态提供一个可重复的 Playwright fixture。比较前统一隐藏光标，等待 `document.fonts.ready`、图片和目标网络响应完成，对非必要动画使用 reduced-motion/禁用样式，并等待两个 `requestAnimationFrame`；禁止用任意 sleep 猜测稳定。测试不访问真实 MiKan、Auto Bangumi 或 qBittorrent。

Stage 46 在 Python dev 依赖中引入一个最小 PNG 解码能力（优先 `Pillow`，写入 `pyproject.toml` dev group 与 `uv.lock`），由测试 helper 在临时目录中完成以下确定性比较；不新增生产依赖，不提交运行时截图、diff 或 trace：

1. 保留六张源 PNG 不变；比较时统一以明确记录的 LANCZOS 参数归一化为 `1440×900`，实际页面截图直接使用 `1440×900`。
2. 对画布、表面、边框、控件和留白等稳定区域，以“任一 RGB 通道差值大于 12”为差异像素，差异像素不得超过参与比较像素的 0.5%。文字字形内部、fixture 海报内部和旋转进度弧可排除，但掩码必须由固定 selector/矩形生成、逐项列名并限制面积；禁止整页、整卡或自由涂抹掩码。**裁决 3C（2026-09-21）：现有六张设计 PNG 与冻结 Design Token V1 存在系统性几何冲突（顶栏 86 vs 72px、品牌左缘 121 vs 20px、导航字号 ≈20 vs 15px、首页控件 70 vs 52px），差异带并集需要 55.14% 命名掩码，超过 35% 上限；按第 2.1 节规格优先级采用冻结 Token，因此 Stage 46 不对这六张 PNG 启用本条 0.5% 硬门禁。** 若要恢复设计图像素级验收，必须先提供并审批一套与冻结 Token V1 一致的新参考图或正式测量基线。
3. 对页头、标题、分段控件、主输入、步骤条、候选卡、审核容器、批量双栏和固定操作栏建立关键锚点表；标准桌面下每个锚点的 `x/y/width/height` 与从归一化设计图量得的目标差异不超过 2 CSS px。文本区域同时断言行数、截断/换行和容器边界，避免掩码隐藏排版错误。
4. 颜色、字号、行高、字重、圆角、边框、阴影、控件高度和焦点环以 Design Token V1/无障碍校正值的 computed style 精确断言；效果图采样色不反向覆盖冻结 token。
5. 若固定 Linux Chromium 的字形边缘仍不稳定，只允许排除字形像素，不允许排除文本容器及基线位置。若上述门槛确实不可重复，必须留下连续三次运行证据并请求调整，不能由实现 Agent 自行放宽。

每个状态还必须保留 DOM、交互、敏感值 canary、键盘、200% 缩放和 `1280×720`/`1920×1080` 响应式测试；截图通过不能替代业务测试。

## 4. 分阶段规划

### Stage 46：像素基线、壳层与设计系统

**目标：** 建立确定性截图夹具、图像比较工具和全页 shell，使 01～06 共用的背景、顶栏、导航、字体、颜色、间距、基础控件可测量、可复用。

1. `US-358`：实现源图归一化、PNG 比较 helper、命名掩码与合成图片边界测试。
2. `US-359`：建立图 01～03 的单番 route mock/held route fixture 与锚点/掩码 manifest。
3. `US-360`：建立图 04～06 的批量 route mock/held route fixture 与锚点/掩码 manifest。
4. `US-361`：按测量结果收口 `App.vue`、壳层 token、品牌/导航/连接状态，并回归四页。
5. `US-362`：收口共享按钮、输入、选择、反馈与分段控件；页面专属结构仍留后续 Stage。

**AC：** 六个 fixture 都能在 `1440×900` 进入准确业务状态，比较器连续三次对同一截图给出相同结果；Stage 46 范围内的顶栏和共享控件满足**冻结 Token 的锚点/computed style/控件尺寸/可访问性**门槛（按裁决 3C 不对现有六张 PNG 启用 0.5% 图像硬门禁）；100%/200% 缩放下导航、跳过链接和焦点均可达。不得改任何业务请求、路由语义或 API。

### Stage 47：单番三状态复刻

**目标：** 对齐图 01～03 的英雄搜索、候选选择与审核页面，同时保持真实候选选择和草案状态机。

1. `US-363`：单番首页——标题/副标题、模式切换、输入搜索组合、三步指示和初始留白。
2. `US-364`：候选选择——搜索摘要、三列候选卡、选中描边、就地 loading、季度确认/失败/空态的同骨架替代状态。
3. `US-365`：草案审核——合集身份卡、筛选与资源双栏、保存修改层级、高级项、最终本地确认区；不删除既有恢复与阻断信息。

**AC：** 图 01～03 在和冻结 Token V1 一致的新参考基线获批后分别达到图像阈值；候选仅在点击后生成草案，其余候选防重复；编辑、冲突、零资源、保存失败、已保存待确认和定位恢复仍就地可用；长标题不溢出，`1280×720` 与 200% 缩放不裁剪焦点或最终操作。

### Stage 48：批量三状态复刻

**目标：** 对齐图 04～06 的批量输入、批量审核左卡右详情、固定确认栏与结果展示，不改变 Stage 45 的确认范围语义。

**AC：** 图 04～06 在和冻结 Token V1 一致的新参考基线获批后分别达到图像阈值；1/12/36 项、隐藏勾选、无资格、筛选无匹配、局部失败、部分成功和 unknown 的行为不变；固定栏不遮挡最后卡片、字段或错误，模态焦点和背景 inert 正确。

## 5. 执行、审核与验证

实施阶段共三个：Stage 46 公共基础、Stage 47 单番、Stage 48 批量。独立视觉审核和跨状态回归是每个 Stage 的质量门禁，不另包装成没有用户价值的 Stage 或 User Story。每个 Stage 先由唯一写入 Agent 完成一个原子工作包与定向验证，再独立审核；问题先用最小红测固定，由同一修复 Agent 集中收口并复审。开发、审核、修复及复审闭环前不切换该工作包写入者。Stage 46 闭环后才进入 Stage 47，Stage 47 闭环后才进入 Stage 48。

每包至少运行受影响 Vitest、`npm run typecheck`、`npm run lint`、`npm run build`，以及项目 `dev-browser` 规范要求的真实 Chromium 定向用例。截图夹具使用 route mock 和临时 storage；不写入 `.migu_orca/storage`，不保存敏感 trace/screenshot。接口或生成代码无预期变更；若实现中发现确需接口字段或改变产品语义，立即停止该包并另行请求决策。

每个 Stage 收尾都核对其目标图的差异结果（Stage 46 为诊断值，Stage 47/48 需先获批与冻结 Token 一致的新基线）、锚点表、掩码面积/理由、非设计状态和共享组件调用者；Stage 48 最终收尾再一次运行仓库规定的完整后端、前端、OpenAPI 与 Chromium 门禁，并执行六图总验收及 `git diff --check`。若任一目标图未达到三层门槛，不得用“视觉方向一致”结案。本 PRD 不授予 push、建 PR、合并、外部写或删除数据的权限。

## 6. 需先确认的决策

1. 设计参考图中的品牌字标和封面是虚构资产。默认采用文字品牌和安全占位/fixture 海报；若必须复制具体图像内容，需要用户提供可使用的源文件及授权。
2. 本 PRD 以项目 CI 的 Linux Chromium 为唯一自动像素真值；macOS/Windows 只做人工观察与功能回归，不共享像素阈值。若需以其他系统为发布基线，应单独建立该环境的参考截图和字体清单。
3. 本 PRD 默认只复刻“添加番剧”。顶部 shell 的共享样式变化会影响追番方案、追番管理和设置，但这些页面不纳入像素复刻，只做不回归验证；若需四页同步改版，应另立范围。

## 7. 二次审核结论

本轮独立复核修正了四项会影响执行真实性的问题：源 PNG 物理尺寸不再误作 CSS viewport；明确当前仓库缺少像素比较器并把测试期工具纳入 Stage 46；将单一整页阈值改为稳定区域、关键锚点和 computed style 三层验收；移除把审核/回归包装成 Stage 49 用户故事的拆分。修订后未发现需要扩展后端或改变既有业务状态机的前置缺口。
