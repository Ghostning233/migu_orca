## 1. 文档状态

| 项目 | 内容 |
| --- | --- |
| 文档类型 | 页面结构讨论稿 / 低保真线框 |
| 当前状态 | 混合方案已选定，页面骨架与详细交互规格均已冻结 |

两套方案均遵守已经确认的业务边界，不把既定产品决策重新包装成视觉选择。
详细组件行为、状态矩阵和后端依赖见
[桌面端前端交互规格](frontend-ux-interaction-spec.md)。

## 2. 两套方案共同不变的部分

1. 一级导航固定为“添加番剧 / 追番方案 / 追番管理 / 设置”。
2. “添加番剧”默认是单番搜索，使用可点击并带滑动动画的分段控件切换批量模式。
3. 单番和批量各自保留输入；单番只能一行，批量自动增高并在达到上限后内部滚动。
4. 批量审核使用左侧卡片列表、右侧共享详情；选择其他卡片直接替换详情。
5. 卡片可直接修改字幕组，并与详情中的同一字段即时同步；服务端重算期间禁止确认该条目。
6. 普通用户只看到“保存并确认”；成功后切换到“追番管理”，新条目仍为“待提交”。
7. 创建 Auto Bangumi 外部订阅必须由用户再次明确提交。
8. 普通编辑展示标题、季度、合集、字幕组和资源摘要；过滤、目录、RSS 与诊断放入高级设置。
9. “全部信息”使用独立悬浮窗，只展示服务端允许公开的安全字段。
10. 未连接 Auto Bangumi 不阻止搜索与方案编辑，到管理或提交时才升级为阻断提示。

## 3. 方案 A：任务引导型

### 3.1 定位

顶部一级导航配合分步骤内容区。页面一次只强调一个主要任务，已经完成的步骤折叠成摘要。
该方案优先照顾首次使用、低频使用和不理解技术术语的用户。

### 3.2 应用外壳

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ MiGuOrca    添加番剧   追番方案   追番管理   设置          ● 服务已连接      │
├──────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│                 居中主内容区，最大宽度约 1280 px                             │
│                                                                              │
└──────────────────────────────────────────────────────────────────────────────┘
```

- 导航始终固定在顶部，当前页面用明显底线或填充态表示。
- 右上角只显示“已连接 / 需要连接 / 连接异常”，不直接展示 endpoint 或账号。
- 页面标题下提供一句任务说明，不展示面包屑和内部对象名称。

- 切换批量模式后输入框向下增长，按钮文案变为“开始批量搜索”。

### 3.9 优点与风险

优点：

- 首屏简单，用户很容易知道第一步应该做什么。
- 单番流程一次只突出一个决定，错误成本低。
- 顶部导航符合普通网站心智，学习成本较低。
- 页面有足够宽度承载批量双栏和详情。

风险：

- 单番搜索、选择和审核之间页面变化较多。
- 高频用户需要多次进入下一步，处理速度略慢。
- 追番方案与追番管理使用卡片列表时，36 个以上历史条目的纵向空间利用率一般。

## 4. 方案 B：持续工作台型

### 4.1 定位

固定左侧一级导航，创建、列表与详情持续保留在同一工作台中。单番和批量共享几乎完全一致的
空间模型，方案优先照顾批量处理效率和频繁管理 Auto Bangumi 的用户。

### 4.2 应用外壳

```text
┌──────────────────┬───────────────────────────────────────────────────────────┐
│ MiGuOrca         │ 当前页面标题                              ● 已连接         │
│                  ├───────────────────────────────────────────────────────────┤
│ ● 添加番剧       │                                                           │
│   追番方案       │                  页面工作区                               │
│   追番管理   2   │                                                           │
│   设置           │                                                           │
│                  │                                                           │
│                  │                                                           │
│ v3.1.18          │                                                           │
└──────────────────┴───────────────────────────────────────────────────────────┘
```

- 侧栏宽约 184～208 px，一级入口和待处理数量长期可见。
- 连接状态靠近侧栏底部；技术版本只有进入连接详情后才显示。
- 主工作区不设置过窄的最大宽度，优先利用 1440～1920 px 横向空间。

```text
│                  │                                   │ [更多操作]            │
└──────────────────┴───────────────────────────────────┴───────────────────────┘
```

- 待提交和失败数量可以显示在一级导航旁，减少遗漏。
- 表格适合大量订阅的扫描、排序和批量刷新。
- 右侧检查器承载启停、编辑和删除；危险操作不直接放在表格行内。

### 4.9 优点与风险

优点：

- 单番、批量、方案和管理页都遵循“列表 + 检查器”，结构高度一致。
- 12～36 部批量审核效率更高，上下文不会因步骤切换而消失。
- 更适合键盘操作、筛选、快速切换和未来完整 Auto Bangumi 管理。
- 追番方案和追番管理可以容纳更多历史条目。

风险：

- 首屏组件和分区较多，对首次用户更像管理软件。
- 1280 px 宽度下侧栏、列表和详情会争抢空间。
- 单番场景也显示列表/详情结构，可能显得过重。
- 如果视觉层级和空状态处理不足，用户可能不知道先操作搜索区还是结果区。

## 6. 已选定方案

已确认以**方案 A 为主、吸收方案 B 的批量工作台能力**：

1. 使用方案 A 的顶部一级导航、简单首页和单番分步骤体验。
2. 批量搜索完成后切换到方案 B 风格的持续双栏工作区，保留异常置顶、标题搜索、状态筛选、
   键盘切换和固定批量操作栏。
3. “追番方案”默认使用方案 A 的宽松列表，但达到较多条目时可以切换紧凑视图。
4. “追番管理”使用方案 B 的状态总览和列表/检查器，因为这里本身就是管理场景。
5. “设置”使用方案 A 的分组卡片；只有高级与诊断区域再使用二级目录。

这不是把两套方案任意拼接，而是让低频创建保持简单，让天然高密度的批量和管理任务获得足够
效率。用户不需要在首次进入时面对完整工作台，但在处理 36 部番剧时也不会被逐步向导拖慢。

## 7. 两套方案共同的关键状态

| 状态 | 页面行为 |
| --- | --- |
| 首次使用 | 搜索框下显示最多三步的简短引导，可关闭，不弹强制教程 |
| 未连接 Auto Bangumi | 页面顶部轻量提醒；允许搜索和编辑，管理/提交时显示连接对话框 |
| 搜索中 | 保留输入，按钮显示进度；已有结果不立即清空，标记为正在更新 |
| 无结果 | 在结果位置说明未找到，并给出修改名称/季度的直接操作 |
| 季数冲突 | 卡片标记“需要核对”，置顶，禁止选入批量确认 |
| 无有效资源 | 卡片标记“无有效资源”，置顶，提供修改字幕组/过滤规则入口 |
| 字幕组重算 | 当前卡片和详情同步显示重算中，临时锁定确认，不锁定其他条目 |
| 保存并确认中 | 锁定本次涉及条目，保留其他页面操作；成功后跳转追番管理 |
| 待提交 | 高亮新条目，明确说明尚未创建 Auto Bangumi 订阅 |
| 提交中 | 禁止重复提交，显示目标番剧和连接状态 |
| 提交失败 | 就地显示原因和重试；不丢失已经保存的方案 |
| 追番中 | 显示启用状态、最近刷新和可用管理操作 |
| 草案过期 | 解释需要重新搜索的原因，尽量保留用户输入和非敏感选择 |
| 批量部分成功 | 成功项进入待提交，失败项原位保留并逐条显示原因，不回滚整批 |
| 提交前失效 | 服务端重新验证失败后阻止外部提交，标记需重新确认并返回对应详情 |
| 离开未保存批次 | 本轮使用离开/刷新警告，不把候选上下文静默持久化为服务端会话 |
| 删除外部订阅 | 默认保留本地方案和历史；明确说明 RSS/任务影响，不删除媒体文件 |

## 8. “全部信息”悬浮窗

两套方案共用同一规格：

```text
                 ┌─────────────────────────────────────────────┐
                 │ Request 全部信息                       [×] │
                 ├─────────────────────────────────────────────┤
                 │ 基本信息                                    │
                 │ 标题、季度、来源、创建时间、当前安全状态    │
                 │                                             │
                 │ 资源与规则                                  │
                 │ 字幕组、过滤摘要、资源统计、季数证据摘要    │
                 │                                             │
                 │ 历史                                        │
                 │ 保存、确认、提交和失败记录                  │
                 ├─────────────────────────────────────────────┤
                 │                                      [关闭] │
                 └─────────────────────────────────────────────┘
```

- 宽度约 720～840 px，高度不超过视口，内容区内部滚动。
- 支持键盘关闭和焦点回到触发按钮。
- 不展示凭据、完整 endpoint、完整 RSS URL、magnet、原始外部响应或本地绝对路径。
- 这是只读信息窗，不在其中复制另一套编辑表单。

## 9. 方案选择结果

混合方案于 2026-09-07 确认，页面骨架按以下规则冻结：

1. 应用外壳采用方案 A 的顶部一级导航。
2. 首页和单番流程采用方案 A 的简单入口与分步骤推进。
3. 批量审核采用方案 B 的持续双栏工作台，并保留异常置顶、筛选、快速定位和固定操作栏。
4. “追番方案”采用方案 A 的宽松列表，数据量较大时允许切换紧凑视图。
5. “追番管理”采用方案 B 的状态总览、列表和右侧检查器。
6. “设置”采用方案 A 的分组卡片，高级与诊断区域可以使用二级目录。

后续组件级交互规格已经补齐卡片层级、详情分区、批量操作栏、筛选与键盘行为、对话框、
加载/错误/恢复状态及页面跳转；整体方向不再重新比较。

同时已经确认：批量保存确认允许逐条部分成功；外部提交前必须由服务端重新验证；本轮只做
未保存批次的离开/刷新警告，不增加服务端恢复会话；删除 Auto Bangumi 外部订阅时保留本地
方案和历史，且不得删除已下载媒体。
