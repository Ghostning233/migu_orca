## 2. “自动重算”与“保存修改”的语义

当前 `preview-modify` 会修改服务端内存中的未保存草案，并返回新 `draft_revision`；最终本地持久化仍由“保存并确认”完成。因此自动展示筛选效果并不是只在浏览器中预演。按本轮要求保留按钮并改称“保存修改”：建议它负责立即提交尚未触发的 1.5 秒待处理输入，以及目录等未自动更新的高级字段；无待处理修改时禁用。按钮附近说明“修改已更新到本次草案，完成审核后仍需保存并确认”，避免被理解为已保存本地方案。自动重算刚完成时，界面应显示“草案效果已更新”，而不是再次要求用户点击按钮才能看见结果。

自动重算必须保留服务端草案权威：以 `draft_id + base_revision` 提交，成功后原子替换字幕组、规则、资源数和 revision；失败保留上一次有效资源并显示“尚未生效”，允许重试或恢复。1.5 秒防抖从最后一次输入开始计算；输入无效时就地解释，不发送无效更新。批量卡与详情共用同一结果。

## 3. 草案详情的信息层级建议

普通用户在这一步主要回答三个问题：**选的是哪部、筛选后能用什么资源、现在能否确认**。据此建议单番与批量右侧详情使用同一核心，只改变容器布局：

1. 顶部“已选合集”：封面、正式标题、季度、合集安全名称或标识、总集数；提供“重新选择合集”。季数冲突或证据不足紧邻标题提示。不要在主视图展示 `request_id`。
2. 中部“字幕与资源”：字幕组选择；有效资源数和少量安全的资源标题样例；“已排除 X 个”及变化状态。包含/排除规则放在相邻的“筛选资源”区域，使修改与结果直接对应。无有效资源时给出原因及下一步，不只显示数字 0。
3. 底部“确认”：当前能否保存、具体阻断原因、唯一强主操作“保存并确认”；说明该操作只建立本地确认方案，外部提交仍在“我的追番”再次确认。批量详情的主保存动作仍由固定操作栏统一承载。
4. 按需展开：完整种子列表按字幕组分组并缩进；正则、大小写与目录等高级选项折叠；诊断、公开历史等仅通过安全白名单“全部信息”展示。未保存草案是否能使用已保存 Request 的 safe-info 接口需先核对契约，不能直接复用不适用的端点。

“已更新集数”目前没有可信数据，只保留清楚的“待开发”占位；总集数有公开数据时显示，否则为“未知”。默认区域不重复展示同一标题、字幕组、规则和资源计数。`Overview / Source / Filter / Seeds`、原始标题、技术 ID 与 RSS 状态不能代替用户任务语言。
