## 2. 项目背景

用户有观看、收藏番剧的需求，目前主要通过 MiKanProject 获取番剧 RSS，并使用 Auto Bangumi 配合 qBittorrent 实现自动下载。

现有成熟工作流大致为：

1. 用户通过番剧推荐视频、季度新番导视等渠道确定想看的新番。
2. 用户手动在 MiKanProject 中搜索番剧。
3. 用户在多个字幕组提供的 RSS 中选择一个符合偏好的 RSS。
4. 用户将 RSS 配置到 Auto Bangumi 中。
5. 用户手动填写订阅名称、目录名称、季度编号、筛选规则等信息。
6. Auto Bangumi 根据 RSS 与用户规则将符合条件的种子添加到下载任务中。
现有流程虽然可用，但每个季度都需要重复执行大量人工操作。每季度用户可能至少需要整理 6 部以上新番，手动搜索、判断字幕组、配置 RSS、命名目录会耗费较多时间，导致整理成本较高。

因此，需要构建一个位于 MiKanProject 与 Auto Bangumi 之间的自动化编排系统，用于自动完成番剧搜索、RSS 分析、字幕组评估、种子筛选、目录命名和 AB 调用前的确认流程。

## 3. 项目目标

本项目目标是实现 MiGuOrca，即一个“新番自动订阅编排系统”。

用户只需要输入自己想看的番剧名称，系统根据预设规则、用户偏好和搜索结果，自动生成一条可确认的订阅 Request。

Request 中需要包含：

1. 系统搜索到的源信息。
2. 系统推荐的可确认配置。
3. 用户可执行的接受、修改、取消操作。
用户确认后，系统调用 Auto Bangumi 完成番剧自动下载配置。

## 4. 项目边界

### 4.1 本项目负责的事情

本项目负责：

1. 通过入口与流程编排模块接收用户输入的单个番剧名称。
2. 搜索并匹配 MiKanProject 中的番剧资源。
3. 获取候选字幕组 RSS。
4. 解析 RSS 中的种子信息。
5. 根据默认种子筛选规则计算有效种子。
6. 根据用户偏好推荐字幕组。
7. 根据命名规则生成预期文件夹名。
8. 生成一条待用户确认的 Request。
9. 支持用户接受、修改、取消 Request。
10. 用户接受后，优先调用 Auto Bangumi 创建订阅任务。
11. Auto Bangumi 调用失败时，降级生成可供后续处理的 AB 配置。
12. 记录 Request 状态、用户修改历史、AB 调用结果和关键日志。

### 4.2 本项目暂不负责的事情

第一阶段暂不负责：

1. 自动从推荐视频中提取用户想看的番剧。
2. 自动判断用户是否真的喜欢某部番剧。
3. 完整的本地媒体库刮削与整理。
4. 视频文件重命名。
5. 播放器集成。
6. 跨平台客户端。
7. 完整字幕组质量评分体系。
8. 复杂 AI 推荐系统。
9. 批量季度清单输入。
10. Web UI。
上述能力可作为后续扩展模块处理。

## 5. 用户场景

### 5.1 核心用户场景

用户看到某部季度新番后，只需要向系统输入：

咒术回战第三季

系统自动执行：

1. 入口与流程编排模块接收输入并启动单番剧订阅流程。
2. 搜索 MiKanProject。
3. 匹配最相似的番剧条目。
4. 获取该番剧下多个字幕组 RSS。
5. 解析每个 RSS 中的种子。
6. 使用默认筛选规则计算有效种子数。
7. 推荐一个字幕组。
8. 生成有效种子名列表。
9. 生成预期文件夹名。
10. 返回一条待确认 Request。
用户看到 Request 后，可以选择：

1. 接受。
2. 修改。
3. 取消。

如果用户发现系统匹配到了错误番剧，则取消当前 Request，并重新输入更准确的番剧名称。

## 6. 核心概念

### 6.1 Request

Request 是本系统的核心业务对象。

一条 Request 表示：

系统根据用户输入、搜索结果、规则和偏好生成的一份“番剧订阅确认单”。

Request 不是一次性展示结果，而是需要有状态、有生命周期、可被修改、可被确认、可被取消的业务对象。

### 6.2 源信息 source_info

源信息是系统搜索、解析、分析后得到的客观信息。

源信息包括：

1. 匹配到的 MiKan 番剧信息。
2. 候选字幕组。
3. 每个字幕组 RSS 地址。
4. 每个 RSS 下的种子总数。
5. 默认筛选规则下的有效种子数。
6. 被排除的种子及排除原因。
7. 有效种子名列表。

### 6.3 待确认配置 confirmable_config

待确认配置是用户可以确认或修改的部分。

包括：

1. 当前选择的字幕组。
2. 当前种子筛选规则。
3. 当前规则下计算出的有效种子名列表。
4. 预期文件夹名。
5. Auto Bangumi 所需的相关配置字段。
其中，有效种子名列表不允许用户直接修改，只能通过修改字幕组或种子筛选规则间接改变。

## 8. Request 状态流转

Request 状态暂定如下：

```text
CREATED
  ↓
SEARCHING
  ↓
PENDING_CONFIRM
  ├── ACCEPTED
  │     ↓
  │   AB_SUBMITTING
  │     ↓
  │   AB_SUBMITTED
  │
  ├── MODIFIED
  │     ↓
  │   PENDING_CONFIRM
  │
  ├── CANCELLED
  │
  └── EXPIRED
```

### 8.1 状态说明

| 状态 | 含义 |
| --- | --- |
| CREATED | Request 已创建，但尚未开始搜索 |
| SEARCHING | 系统正在搜索 MiKan、解析 RSS、计算结果 |
| PENDING_CONFIRM | Request 已生成，等待用户确认 |
| MODIFIED | 用户修改了可修改字段，系统需要重新生成 Request |
| ACCEPTED | 用户已接受 Request |
| AB_SUBMITTING | 系统正在调用 AB |
| AB_SUBMITTED | AB 调用成功，订阅已创建 |
| CANCELLED | 用户取消 Request |
| EXPIRED | Request 过期，需要重新生成 |

### 8.2 接受前校验

用户点击接受时，系统需要重新校验 RSS 信息。

原因：

1. RSS 内容可能发生变化。
2. 有效种子列表可能增加或减少。
3. 字幕组可能更新了修正版。
4. 用户看到的 Request 可能已经不是最新状态。
接受前校验规则：

1. 重新拉取当前选择字幕组的 RSS。
2. 重新应用当前筛选规则。
3. 对比有效种子列表是否发生关键变化。
4. 若无关键变化，则调用 AB。
5. 若有关键变化，则重新生成 Request，并要求用户再次确认。

## 9. 用户操作定义

### 9.1 接受

用户接受当前 Request。

系统行为：

1. 将 Request 状态更新为 ACCEPTED。
2. 执行接受前校验。
3. 校验通过后调用 Auto Bangumi。
4. 调用成功后更新为 AB_SUBMITTED。
5. 调用失败后记录失败原因。

### 9.2 修改

用户修改当前 Request 的可修改信息。

可修改字段包括：

1. 选择的字幕组。
2. 种子筛选规则。
3. 预期文件夹名。
4. 部分 AB 所需配置项。
不可直接修改字段包括：

1. 有效种子名列表。
2. RSS 中原始种子信息。
3. MiKan 原始搜索结果。
系统行为：

1. 接收用户提交的修改补丁。
2. 应用修改补丁。
3. 重新计算有效种子列表。
4. 重新生成 Request。
5. 返回新的待确认 Request。

### 9.3 取消

用户取消当前 Request。

常见原因：

1. 用户输入的番剧名未正确匹配。
2. 系统匹配到了错误番剧。
3. 匹配到了番剧，但没有合适字幕组。
4. RSS 中没有有效种子。
5. 用户暂时不想订阅该番剧。
系统行为：

1. 将 Request 状态更新为 CANCELLED。
2. 记录取消原因。
3. 不调用 AB。

## 13. 整体架构设计

### 13.1 架构目标

系统整体架构需要满足：

1. 模块边界清晰。
2. 规则可配置。
3. 外部系统可替换。
4. Request 状态可追踪。
5. 搜索、解析、筛选、确认、提交流程可拆分。
6. 后续可以从当前入口与流程编排模块平滑扩展到 Web UI。
7. 后续可以扩展更多数据源，不强绑定 MiKan。
8. 后续可以替换 AB 集成方式，不强绑定某一种调用方式。

### 13.2 初步分层

```text
用户交互层
  ↓
应用服务层
  ↓
领域逻辑层
  ↓

  ↓
外部系统
```

### 13.3 各层职责

#### 13.3.1 用户交互层

负责：

1. 作为入口与流程编排模块的外部触发入口。
2. 接收单个番剧名称输入。

7. Clients 是带用户认证或权限边界的 API 接口，用户侧能力调用应通过 clients 暴露。
8. services 和 clients 主要为后续 Web UI 或 API 化预留，MVP 阶段只需在框架中定义清楚。
9. 测试文件与被测逻辑文件放在同一目录下，测试文件名以 _test 结尾。
10. 项目整体采用 TDD 方式开发，新增或修改业务逻辑前应先补充对应测试。
11. 目录结构只表达项目架构，不在主 PRD 中列举所有具体代码文件。
12. tools/ 只表示外部服务调试脚本目录，不在主 PRD 中绑定具体脚本文件名。

### 14.2 src 分层说明

src/ 下分为 engine 模块和 apps 两类目录。

| 路径 | 职责 |
| --- | --- |
| src/*_engine/ | 核心业务能力实现层，按业务 engine 拆分 |
| src/apps/ | 统一 API 管理层，按 engine 模块封装 services 和 clients |
| src/apps/migu_orca_entry/ | 入口与流程编排模块，负责串联完整业务流程 |

分层原则：

1. engine 模块直接位于 src/ 下，负责实现业务能力。
2. apps 负责把业务能力封装成可调用 API。
3. 入口编排模块可以直接调用 engine Controller 完成 MVP 流程。
4. 后续做 Web UI 或 API 服务时，由 apps 层统一对外提供 services 和 clients。
5. 业务规则不应写在 apps 层，apps 层只做参数传递、调用编排、权限边界和返回包装。

### 14.3 engine 内部结构规范

每个 engine 内部遵循 MVC 风格组织。

| 目录 | 职责 |
| --- | --- |
| models/ | 定义该 engine 的数据模型、值对象、状态对象 |
| controllers/ | 定义该 engine 的业务能力入口，供入口编排模块或 apps 层调用 |

Controller 的职责：

1. 作为 engine 的唯一或主要业务能力入口。
2. 屏蔽 engine 内部 models 和具体实现细节。
3. 向入口编排模块提供稳定的业务能力接口。
4. 承担本 engine 内部业务流程组织，但不处理用户认证或用户侧 API 暴露。

入口编排模块职责：

1. 接收单番剧业务流程启动请求。
2. 调用 Request、MiKan、RSS、筛选、命名、确认、AB、存储、日志等 engine 的 Controller。
3. 串联各 engine 能力，形成完整业务流程。
4. 不直接实现各 engine 的内部业务规则。

### 14.4 apps API 层结构规范

apps 层用于统一管理 API 封装能力。

| 目录 | 职责 |
| --- | --- |
| services/ | Controller 业务能力的 API 封装，仅供系统内部使用 |
| clients/ | 带用户认证、权限边界或用户侧调用约束的 API 接口 |

Services 的定义：

1. Services 封装 Controller 的业务能力。
2. Services 负责接收必要参数、调用对应 Controller、整理返回结果。
3. Services 只允许在系统内部使用，不直接作为用户侧调用入口。
4. Services 不承载核心业务规则，核心规则仍归属于 engine。

Clients 的定义：

1. Clients 是带用户认证或权限边界的 API 接口。
2. 用户侧能力调用只能通过 Clients 暴露。
3. Clients 可以调用 Services，但不应直接绕过 Services 操作 engine 内部结构。
4. Clients 主要服务后续 Web UI、API 服务或外部调用场景。

MVP 阶段处理原则：

1. 当前 MVP 不实现 Web UI。
2. apps 层先定义目录职责和边界。
3. 如当前流程不需要 API 化，可以暂不实现具体 services 和 clients。
4. 等 Web UI 或 API 服务进入范围后，再补充具体接口设计。

### 14.6 测试文件规范

测试文件不单独集中到 tests/ 目录，而是与被测逻辑文件放在同一目录下。

TDD 规则：

2. 修改已有业务规则前，先补充或调整能复现目标行为的测试。
3. 修复缺陷前，先补充能复现缺陷的失败测试。
4. 测试通过后再整理实现代码。

命名规则：

1. 被测逻辑文件与测试文件同目录。
2. 测试文件名在被测逻辑文件名后追加 _test。
3. 每个 engine 自己维护自己的测试文件。

```text
      request_model
```

## 15. MVP 范围

### 15.1 MVP 必须支持

MVP 阶段需要支持：

1. 入口与流程编排模块可以启动单番剧订阅流程。
2. 用户输入单个番剧名称。
3. 系统通过 MiKanProject 爬虫搜索番剧。
4. 系统自动选择最相似的番剧匹配结果。
5. 系统获取该番剧下的字幕组 RSS。
6. 系统解析 RSS 种子。
7. 系统根据默认筛选规则计算有效种子。
8. 系统推荐一个字幕组。
9. 系统生成预期文件夹名。
10. 系统生成 Request。
11. 用户可以接受、修改、取消 Request。
12. 用户接受后，系统调用 AB 创建订阅。
13. AB 调用失败时，系统可以生成降级 AB 配置。
14. 系统可以持久化 Request、状态、操作历史和 AB 调用结果。
15. 系统可以通过配置文件记录用户的部分偏好和规则信息。
16. 系统具备独立日志能力，用于开发排错。

### 15.2 MVP 可以简化

MVP 阶段可以简化：

1. 字幕组评估先使用固定优先级。
2. 文件夹命名先使用模板。
3. 用户偏好先使用配置文件。
4. Request 展示先由入口与确认交互模块提供最小展示能力。
5. 搜索匹配先直接使用最相似结果，不提供候选番剧手动选择。
6. 不做复杂历史学习。
7. 不做本地媒体库管理。
8. 不做 Web UI。
9. 不做批量季度清单输入。

## 19. 异常场景

系统需要处理以下异常：

1. 搜索不到番剧。
2. 搜索到多个相似番剧时，系统选择了错误匹配。
3. 匹配到错误番剧。
4. MiKan 无法访问。
5. MiKan 页面结构变化导致爬虫解析失败。
6. RSS 无法拉取。
7. RSS 格式异常。
8. RSS 中没有种子。
9. 默认规则下有效种子数为 0。
10. 所有字幕组均不符合偏好。
11. 文件夹名生成失败。
12. 用户修改后规则冲突。
13. 用户接受时 RSS 内容发生变化。
14. AB 调用失败。
15. AB 调用失败后降级配置生成失败。
16. AB 返回成功但订阅未实际创建。
17. 持久化写入失败。
18. 日志写入失败。
19. Request 过期。

MVP 阶段失败处理原则：

1. 系统记录失败原因。
2. 系统不自动重试完整流程。
3. 如果用户希望重试，需要重新输入番剧名并重新跑一遍完整流程。

## 20. 全局验收标准

整体项目 MVP 验收标准：

1. 入口与流程编排模块可以接收一个番剧名称，并启动单番剧订阅流程。
2. 用户输入一个番剧名称后，系统可以生成一条 Request。
3. Request 中包含匹配到的番剧信息。
4. Request 中包含候选字幕组列表。
5. Request 中包含每个字幕组 RSS 下的种子总数。
6. Request 中包含默认规则下的有效种子数。
7. Request 中包含当前选择字幕组。
8. Request 中包含当前筛选规则。
9. Request 中包含当前有效种子名列表。
10. Request 中包含预期文件夹名。
11. 用户可以接受 Request。
12. 用户可以修改 Request 中的可修改字段。
13. 用户修改后，系统可以重新生成 Request。
14. 用户可以取消 Request。
15. 用户接受后，系统可以调用 AB 创建订阅。
16. AB 调用失败时，系统可以生成降级 AB 配置。
17. 系统可以记录 Request 状态和 AB 调用结果。
18. 系统可以持久化 Request、状态、操作历史和关键结果。
19. 系统可以持久化用户配置文件。
20. 系统可以将所有日志写入文件。
21. 系统可以根据当前执行场景向控制台输出必要信息。
22. 系统失败时可以记录明确失败原因，但不自动重试完整流程。
23. 系统可以在关键失败场景下给出明确错误原因。

## 21. 非功能需求

### 21.1 可维护性

1. 每个模块必须有清晰边界。
2. 核心规则不能散落在流程代码中。
3. 外部系统访问必须通过适配器封装。
4. Request 状态流转必须集中管理。
5. 用户偏好必须可配置。

### 21.2 可测试性

1. 项目整体采用 TDD 开发方式。
2. 新增或修改业务逻辑前，应先补充对应测试。
3. 规则模块需要可单独测试。
4. MiKan、AB 等外部系统调用需要可替换为测试适配器。
5. Request 状态流转需要有单元测试。
6. 种子筛选规则需要覆盖典型命名格式。
7. 文件夹命名规则需要覆盖用户自定义场景。
8. 测试文件与被测逻辑文件放在同一目录下，测试文件名以 _test 结尾。

### 21.3 可扩展性

1. 后续可以新增其他番剧数据源。
2. 后续可以新增其他下载管理器。
3. 后续可以新增更多字幕组评分指标。
4. 后续可以支持批量季度番剧订阅。
5. 后续可以支持历史偏好学习。

### 21.4 可观测性

1. 每条 Request 需要有完整状态记录。
2. 每次外部系统调用需要记录结果。
3. 每次筛选种子需要记录排除原因。
4. 每次用户修改需要记录修改内容。
5. 失败场景需要有可读错误信息。

## 22. 合规说明

本系统定位为 RSS 订阅自动化与下载流程编排工具。

用户需要自行确保订阅源、下载内容、收藏行为符合当地法律法规及内容授权要求。

系统本身不内置受版权保护内容，不提供资源分发能力，只对用户配置的数据源进行流程编排。

## 25. 当前结论

本项目应优先围绕 Request 这一核心对象进行设计。

第一阶段不要追求完全自动化，而是先完成：

```text
入口与流程编排模块接收单个番名
  ↓
系统通过 MiKan 爬虫搜索和分析
  ↓
生成 Request
  ↓
用户确认
  ↓
调用 AB
  ↓
失败时生成降级 AB 配置
```

只要这个闭环稳定，后续字幕组偏好、命名规则、批量季度整理、历史偏好学习、Web UI 都可以逐步扩展。
