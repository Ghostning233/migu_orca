## 2. 重构定位

MiGuOrca 的核心价值不是展示后端对象，而是帮助用户完成一条可审核的订阅编排流程：

```text
输入单个或一批新番名称
  → 理解标题与季数
  → 搜索并人工选择真实 MiKan 合集
  → 审核字幕组、过滤规则、目录和种子
  → 保存并确认订阅方案
  → 显式提交 Auto Bangumi
  → 处理失败、重试或异常恢复
```

Stage 27 完成的是前端工程化迁移和旧功能对等。下一轮工作的重点不是再次更换框架，
而是让信息架构、任务阶段、页面反馈和视觉层级真正服务上述流程。

首页首先服务随时添加一部番剧的简单场景，批量模式服务低频但信息密度较高的“季度集中整理”。
用户可能隔数月才使用一次批量能力，因此两种模式都不能依赖用户记住技术字段、隐藏入口或
内部状态机。

## 3. 总体目标

### 3.1 已确认的产品与体验决策

1. **目标用户**：主要是“想看番剧的人”，默认不具备 Auto Bangumi、RSS、Request、
   storage 或 API 等技术知识。设计标准是零技术前置、低认知负担、强防错和明确下一步。
2. **近期平台**：当前只开发桌面端。移动端不是近期目标；未来移动端只作为已部署桌面端
   MiGuOrca 的远程管理界面，不在移动端承担部署后端的职责。
3. **默认入口**：首页默认进入单番剧搜索。
4. **模式切换**：首页提供一个选中态明确的滑动分段控件，在“单番搜索”和“批量搜索”之间
   切换；点击标签也触发同一滑动动画，并支持键盘操作与 `prefers-reduced-motion` 降级。
5. **统一输入**：两种模式复用同一输入组件与输入语义。单番模式限制为一行；批量模式允许
   换行，并随输入内容自动增高，达到设计确定的最大高度后在输入框内部滚动。
6. **批量呈现**：每个番剧对应一张审核卡片。卡片只展示完成当前判断所需的信息，主要编辑
   放在独立的详情编辑区域。
7. **字幕组快捷编辑**：批量卡片可以直接通过下拉框修改字幕组；卡片和详情编辑区域必须共享
   同一份草案状态，任一处修改后另一处立即同步，并以服务端重算结果为最终事实。
8. **完整信息查看**：卡片和详情默认保持简洁；提供“全部信息”入口，在悬浮窗口中展示该
   Request 所有允许展示的信息。这里的“全部”仅指服务端公开白名单内的安全信息，不包含
   凭据、敏感 endpoint、完整 RSS URL、magnet、原始外部响应或本地绝对路径。
9. **一级导航**：采用“添加番剧 / 追番方案 / 追番管理 / 设置”。四个页面分别
   承担创建、本地方案、Auto Bangumi 实际订阅和低频配置，不混放业务提交与设置。
10. **Auto Bangumi 页面**：建立统一的“追番管理”页面。以已经核对源码的 Auto Bangumi
    3.1.18 为首个完整适配基线，目标范围包含待提交任务、提交/重试、已有订阅列表与详情、
    修改、启用/停用、删除和手动刷新；其他版本通过能力探测兼容或明确降级。
11. **保存与确认**：普通用户只看到“保存并确认”一个主操作。成功后自动切换到“追番管理”，
    定位刚确认的番剧并显示“待提交到 Auto Bangumi”。后端仍保留保存和接受的不同语义，
    但应提供组合端点，避免前端串联两次请求造成中间失败。
12. **模式输入保留**：单番和批量模式各自保留输入。切换模式不清空另一模式内容；从多行批量
    切回单番时不截断数据，再次切回批量仍可继续编辑。
13. **批量详情复用**：批量卡片列表共享单番详情编辑核心。选择一张卡片时显示该番剧详情，
    选择另一张时直接替换详情内容；不能复制第二套字幕组、过滤和种子编辑逻辑。
14. **卡片最小信息**：卡片默认展示封面、标题、季度、审核状态、字幕组下拉框、有效资源数、
    已更新集数/季度总集数和主要操作。当前没有可靠的已更新集数时保留明确的“待开发”占位，
    总集数有公开数据时正常展示，否则显示未知。
15. **提交边界**：“保存并确认”不会自动创建 Auto Bangumi 外部订阅。跳转“追番管理”后，
    新条目处于“待提交”，由用户明确执行“提交到 Auto Bangumi”。
16. **批量桌面布局**：采用左侧审核卡片列表、右侧共享详情编辑区。详情区在列表滚动时保持
    可见，当前选择改变时直接替换内容。
17. **批量规模**：1 部必须正常可用，典型批量约 12 部，并为最多 36 部一批做好设计和验证。
    36 部规模优先采用状态筛选、异常聚合、快速定位和连续滚动，不默认分页；只有性能验证证明
    必要时才引入虚拟滚动。
18. **批量审核策略**：默认把需要人工处理的异常项排在前面。正常匹配项允许直接批量确认；
    季数冲突、无有效资源等阻断性异常必须打开详情并解决后才能确认。
19. **连接引导**：未连接 Auto Bangumi 时不阻止搜索和方案编辑，只显示轻量、可操作的连接
    提醒；进入追番管理或实际提交时再要求连接。首次使用采用简短的三步引导，不展示技术术语。
20. **字段分层与凭据**：普通编辑展示标题、季度、合集、字幕组和资源摘要；过滤规则、目录、
    RSS 与诊断信息放入高级设置。临时凭据只允许在当前页面会话的内存中复用，刷新或离开后
    清除，不写入 URL、浏览器持久化存储或日志。
21. **低保真结构**：采用混合方案。应用外壳使用顶部导航，首页和单番使用简单入口与分步骤
    推进；批量审核使用持续双栏工作台；追番方案使用宽松列表；追番管理使用状态总览、列表与
    右侧检查器；设置使用分组卡片。
22. **批量部分成功**：批量“保存并确认”采用逐条结果语义。成功条目进入“待提交”，失败条目
    原位保留并显示具体原因，不因为少数失败回滚整批，也不得把失败条目标成已确认。
23. **提交前复核**：提交到 Auto Bangumi 前必须由服务端重新验证方案、候选及必要上下文。
    已过期或失效时阻止外部提交，标记为“需重新确认”，并深链回对应详情处理。
24. **批量恢复范围**：本轮不增加可恢复的服务端批量工作会话。对尚未保存确认的工作提供明确
    离开/刷新警告；服务端恢复会话作为独立后端阶段评估，必须先定义数据生命周期、清理策略和
    敏感上下文边界。
25. **外部删除边界**：删除操作默认只删除 Auto Bangumi 外部订阅，保留 MiGuOrca 本地追番
    方案与历史。确认窗口必须说明是否连带 RSS 或任务，且永远不得删除已下载媒体文件。

未来移动管理端需要访问用户自行部署的桌面端后端，这会改变当前 local-only 的安全前提。
它必须在后续独立评估认证、授权、HTTPS、设备配对和远程访问边界，不能在本轮桌面设计中
默认后端已经可以安全暴露到公网。

### 3.2 重构目标

1. 以“创建订阅 → 审核方案 → 提交与恢复”为主线重组页面，而不是按 API 或存储对象分区。
2. 以单番搜索作为默认入口，通过同一输入组件平滑切换到批量审核流程。
3. 让用户随时知道当前处于哪一步、哪些条目需要处理、下一步会产生什么影响。
4. 优先展示标题、候选、字幕组、有效种子数和是否可提交；技术 ID 与诊断信息渐进披露。
5. 保持用户最终选择合集、确认季数和显式外部提交的安全边界。
6. 复用现有 Vue、OpenAPI、Flask API、领域规则与测试资产，不在前端复制后端业务规则。
7. 建立“讨论设计 → 生成效果图 → 设计确认 → 前端实现 → 独立验收”的协作链路。

## 4. 非目标与边界

本轮前端体验重构默认不包含：

1. 更换 Vue 3、TypeScript 或 Vite。
2. 重写 MiKan、RSS、Request、季数证据或 Auto Bangumi 的领域逻辑。
3. 绕过 Auto Bangumi 直接创建 qBittorrent 下载任务。
4. 真实 LLM Provider、当前播出集数、新版 Bearer 写契约或流式封面代理。
5. 多用户、权限体系、数据库、后台 Worker 或公网 SaaS 化。
6. 为了恢复页面而把凭据、endpoint、`candidate_context` 或 `draft_id` 写入 URL、日志、
   localStorage、sessionStorage 或持久化 Pinia。
7. 近期移动端页面、移动端远程管理和为其配套的认证/公网暴露能力。

效果图用于确认视觉方向和空间关系，不是业务规格的唯一事实来源。交互、状态、无障碍、
响应式和安全约束必须同时记录在设计文档中，不能要求实现 Agent 根据一张图片自行猜测。

## 5. 重构前必须核实或修复的问题

以下事项会影响真实用户流程，应在视觉重构开始前完成事实确认，并按评审结果修复或明确删除：

### 5.1 P0 流程断点

1. 批量解析将 `batch_id` 写入 `/workbench?batch_id=...`，但顶部“提交队列”跳转不携带
   `batch_id`，工作台也没有“进入本批次提交队列”的上下文按钮。
2. 队列页没有批次标识时只有空状态；如果未来定位为独立“提交中心”，需要评估增加最近
   批次或队列列表 API，而不是要求用户记住 URL。
3. 批量审核卡片不持久化，刷新只能恢复已经建立的队列，不能恢复候选与草案现场。
   本轮实现离开/刷新保护，不新增服务端工作会话；可恢复会话留作独立后端阶段，并要求先设计
   数据生命周期、清理策略和敏感上下文边界。

### 5.2 P0 功能真实性

1. “默认保存订阅方案”偏好目前存在 UI，但候选生成固定走未保存草案。既然普通流程已经确定
   使用“保存并确认”，该偏好应删除；保存不再是需要用户预先配置的可选行为。
2. 后端已有标题修正读取/保存接口，但当前 Vue 业务代码没有接回查看、提交或接受时记录修正。
3. “复用已保存修正”开关已经可保存，但需要核实并修复其对批量解析行为的实际控制。
4. 批量解析会展示偏好命中信息，但最终选择候选生成 Request 时是否继承 Web 偏好存在链路缺口，
   必须通过代码和端到端测试确认后修复。
5. “已更新集数”仍是待开发能力；本轮只允许使用统一占位，不得根据种子数、RSS 数量或下载
   状态猜测。效果图也必须把它标为占位能力。

### 5.3 文档事实同步

README 仍包含旧 `/index` 单页结构、已删除的 Fixture 前端入口、旧批量草案骨架和旧草案所有权
描述。正式设计讨论应以当前代码、API 契约和自动化测试为准，完成设计后同步用户文档。

## 6. 需要单独开展的页面体验设计工作

页面设计必须作为独立工作进行，不与生产代码实现混在同一个任务中。该工作至少需要讨论并
明确以下问题。

### 6.1 用户与场景

已确认：面向零技术基础的番剧用户，当前只设计桌面端；首页默认单番搜索，并可滑动切换为
批量搜索。批量规模按 1～36 部设计，典型场景约 12 部。用户首先核对候选正确性、季度、
字幕组和有效资源，过滤规则、目录与诊断信息渐进披露。首次进入提供简短三步引导；Auto
Bangumi 未连接不阻止搜索，只在需要管理或提交时升级为阻断提示。

### 6.2 信息架构候选

已确认一级导航采用四项结构：

```text
添加番剧 | 追番方案 | 追番管理 | 设置
```

“我的方案”最终确定为“追番方案”。候选比较保留如下，作为命名决策记录：

| 名称 | 优点 | 风险 |
| --- | --- | --- |
| 追番方案（已选定） | 与“追番管理”形成准备阶段→生效阶段的自然关系 | 首次使用需要解释方案尚未等于已订阅 |
| 订阅方案 | 准确并沿用现有术语 | 容易和 Auto Bangumi 中的实际订阅混淆 |
| 番剧方案 | 简单、非技术化 | 没有明确表达订阅用途 |
| 方案库 | 适合历史列表 | 对零技术用户较抽象 |
| 我的清单 | 最生活化 | 容易被误解成收藏夹 |

先前比较过的结构保留为决策记录：

| 方案 | 导航 | 特点 |
| --- | --- | --- |
| A（已选定结构） | 添加番剧 / 本地方案页 / 追番管理 / 设置 | 用户任务边界清楚，能区分本地方案与 Auto Bangumi 已生效订阅 |
| B（极简） | 订阅 / 追番管理 / 设置 | 导航少，但创建和历史方案要放在“订阅”的二级结构中 |
| C（按状态） | 订阅工作台 / 待处理 / 已生效 / 设置 | 进度直观，但失败、恢复和本地已接受未提交状态较难归类 |

方案 A 及第二项名称均已确认：

- “添加番剧”承载单个/批量模式和五阶段流程。
- 本地方案页承载 MiGuOrca 已生成的订阅方案，提供查看、修改、复制再用和方案历史；如果方案
  已进入提交或追番阶段，则显示状态并链接到“追番管理”，不在两个页面重复提供运行操作。
- “追番管理”统一单方案和批量提交、失败重试与异常恢复，并在后端能力补齐后管理
  Auto Bangumi 中已有的订阅。
- “设置”只保留默认规则、存储偏好和连接诊断，不执行具体订阅提交。

Auto Bangumi 管理页的名称候选：

| 名称 | 优点 | 风险 |
| --- | --- | --- |
| 追番管理（当前推荐） | 对普通番剧用户直观，可覆盖提交、启停、编辑和删除 | 需要副标题说明数据来自 Auto Bangumi，避免和方案库混淆 |
| 自动订阅 | 能解释 Auto Bangumi 的用途 | 容易被理解为一个开关或配置页 |
| 订阅中心 | 覆盖范围广、产品化 | 与本地“方案库”语义接近 |
| 已订阅番剧 | 最容易理解最终结果 | 不容易容纳待提交、失败和恢复任务 |
| Auto Bangumi | 对已有用户最精确 | 对零技术基础用户不友好，且直接暴露产品名 |

已核对 Auto Bangumi 3.1.18 的
[Bangumi API](https://github.com/EstrellaXD/Auto_Bangumi/blob/3.1.18/backend/src/module/api/bangumi.py)
和 [RSS API](https://github.com/EstrellaXD/Auto_Bangumi/blob/3.1.18/backend/src/module/api/rss.py)：
该版本提供番剧列表/详情/修改/启用/停用/删除，以及 RSS 列表/修改/启用/停用/删除/刷新接口，
因此目标能力具有实现基础。但 MiGuOrca 当前 adapter 只接入登录、状态和创建订阅；正式承诺前
仍需建立版本化 adapter、严格 DTO、脱敏 fixture、外部 ID 映射、幂等与危险操作确认。新版
Auto Bangumi 也必须通过 capability 探测适配，不能假设各版本写接口完全一致。

因此“追番管理”不再按仅提交功能设计，而按完整管理闭环设计。3.1.18 是首个需要完整验收的
版本；其他版本即使能够登录，也只有在 capability 探测确认对应能力后才显示相关操作。

### 6.3 流程与状态语言候选

单个流程候选：

```text
1 输入 → 2 选择合集 → 3 审核草案 → 4 保存并确认 → 5 追番管理中提交
```

批量流程候选：

```text
1 批量输入 → 2 解决异常项 → 3 审核草案 → 4 批量保存并确认 → 5 提交
```

需要建立统一的用户可见状态词，避免 `PARSED`、`FOUND`、`PENDING_CONFIRM`、
`READY_TO_SUBMIT` 等内部状态直接控制用户心智。创建和审核过程的候选语言包括：

```text
待匹配 | 需核对 | 编辑中 | 待提交 | 提交中 | 追番中 | 提交失败 | 需人工恢复
```

#### “保存”和“确认”的产品语义

- **保存**：把草案持久化，允许稍后恢复编辑；不代表用户认可匹配结果、字幕组、过滤规则和
  存储目录。
- **确认**：用户明确认可当前方案，允许它进入可提交到 Auto Bangumi 的队列。

两者在后端仍有不同价值：审计记录、失败恢复、旧数据兼容和外部提交前的安全边界都依赖这个
区别。但针对当前目标用户，没有必要把它们设计成两个连续按钮或两个必须理解的页面状态。
普通流程只提供一个“保存并确认”主按钮，并由一个组合 API 完成校验、持久化和接受；成功后
自动切换到“追番管理”并定位新条目。用户可见状态优先简化为：

```text
编辑中 → 待提交 → 提交中 → 追番中
                         ↘ 提交失败
```

`PENDING_CONFIRM` 等中间状态继续保留在内部，只有发生恢复性异常时才转换成用户能理解的提示。
如果“保存成功、确认失败”，页面应保留已保存结果并提供“重试确认”，不得要求用户重新搜索。

### 6.4 关键页面问题

1. 已确认使用统一输入和滑动分段控件，两种模式各自保留内容；初始焦点和动画时长在线框及
   交互规格阶段确定。
2. 单番详情编辑核心如何抽成可复用组件，使单番页面和批量右侧详情使用同一套状态与动作？
3. 批量审核默认按“需人工处理优先”排序，并允许只查看异常项；正常项可直接批量确认，
   阻断性异常必须进入详情处理。
4. 已确认批量卡片展示封面、标题、季度、状态、字幕组、有效资源数、已更新集数/季度总集数
   和主要操作；仍需在线框阶段确定密度、层级和“待开发”占位样式。
5. 卡片字幕组变更期间是否锁定“保存并确认”，怎样展示服务端种子重算的加载、成功和失败？
6. 详情采用右侧固定区域；选择不同批量卡片时替换当前详情。“全部信息”悬浮窗保持独立，
   只承担完整安全信息查看。
7. 批量操作栏是否固定在页面底部，并持续展示已选、可确认、需核对和失败数量？
8. 方案库在桌面端是否使用左侧列表、右侧详情？
9. Auto Bangumi 管理目标已覆盖连接诊断、待提交队列、提交结果、读取、编辑、启停、删除和
   手动刷新；3.1.18 作为首个完整适配基线，其他版本按能力探测结果降级。
10. 普通编辑展示标题、季度、合集、字幕组和资源摘要；过滤规则、目录、RSS 与诊断信息放入
    高级设置。
11. 敏感凭据在一次页面会话的内存中临时复用，刷新或离开后清除，不进入持久化状态。
12. 页面离开、刷新、草案过期和候选上下文过期时，怎样让用户提前知情并安全恢复？

### 6.5 设计原则候选

以下原则需要在讨论中验证，而不是直接视为最终方案：

- 异常优先：批量场景优先暴露无结果、季数冲突、低置信度和无有效种子的条目。
- 渐进披露：普通模式展示业务信息，高级模式再展示技术字段和完整诊断。
- 单一主操作：每个步骤只有一个最明确的下一步，危险操作弱化并二次确认。
- 上下文连续：从候选到草案、从确认到提交不得依赖用户手工复制 ID。
- 状态就地：关键状态留在页面，Toast 只用于短暂完成反馈。
- 可恢复：能恢复的状态通过公开 ID 恢复；不能安全持久化的状态明确提示生命周期。
- 可访问：键盘、焦点、语义标签、颜色对比和缩减动画进入设计稿；滑动切换不能只靠动画
  或颜色表达当前模式。

## 7. Agent 协作流程

为避免实现细节污染产品决策上下文，项目管理会话主要负责目标、取舍、设计评审、PRD 和阶段验收；
页面设计、效果图生成、前端实现与独立验收应在各自的 Agent / 会话中完成。各执行 Agent 只向
项目管理会话回传结论、产物路径、验证证据、设计偏差和待决策事项，不回灌无关的长代码上下文。

### 7.1 产品与 UX 讨论 Agent

职责：

1. 基于当前代码和 API 事实，与项目负责人逐项讨论用户、场景、导航和核心流程。
2. 对重要问题至少提出两个可比较方案，说明收益、成本、风险和所需后端变化。
3. 维护用户旅程、页面地图、状态矩阵、低保真线框和设计决策记录。
4. 明确桌面目标宽度、空状态、加载、错误、过期、冲突、失败和恢复状态。
5. 不编写生产前端代码，不擅自把候选方案标记为已批准。

输出：经负责人确认的《前端体验设计规格》，以及可交给图像生成 Agent 的视觉设计简报。

### 7.2 具备图像生成能力的视觉 Agent

启动条件：产品与 UX 讨论完成，页面地图、关键交互和视觉简报通过评审。

职责：

1. 先为同一套信息架构生成少量可比较的视觉方向，不重新发明业务流程。
2. 根据选定方向生成关键桌面页面效果图；本轮不以移动页面作为交付要求。
3. 覆盖正常状态之外的“需核对、无结果、提交失败、需人工恢复”等关键业务状态。
4. 输出颜色、字体、间距、圆角、阴影、状态色和组件外观建议，供设计 token 落地。

建议效果图清单：

- 创建订阅首页：单个/批量输入。
- 批量候选与异常优先审核。
- 单项草案编辑与种子摘要。
- 方案库的列表—详情布局。
- 提交中心及失败/恢复状态。
- 设置与连接诊断。
- 至少覆盖设计阶段确认的两档桌面宽度，并体现窗口变窄时的合理布局变化。

效果图评审后必须把确认结果回写设计规格；不能只把图片路径交给实现 Agent。

### 7.3 前端实现 Agent

启动条件：设计规格和选定效果图均通过评审，功能真实性问题已有结论，API 变化已经冻结。

输入材料：

1. 已批准的体验设计规格、页面地图、状态矩阵和响应式规则。
2. 已批准的效果图与设计 token。
3. 当前 OpenAPI 契约、领域状态映射和安全边界。
4. 需要保留的现有浏览器旅程及新增验收矩阵。

职责：

1. 优先复用现有 API client 和领域 helper，按 feature slice 逐步实现。
2. 将大型页面拆为流程 composable 和领域组件，例如候选浏览器、草案编辑器、种子摘要、
   凭据对话框、队列项和状态概览。
3. 每个切片同时完成 TypeScript、Vitest、Playwright、响应式和无障碍验证。
4. 不根据效果图猜测缺失状态，不把后端领域判断复制进组件。
5. 不擅自修改已经确认的流程；发现设计无法实现时返回设计评审处理。

### 7.4 验收 Agent

建议由未承担主要实现的 Agent 独立执行：

1. 对照设计规格检查流程、文案、布局和状态覆盖。
2. 运行单个与批量从输入到提交的真实 Chromium 旅程。
3. 验证刷新、返回、深链接、过期、失败、重试和人工恢复。
4. 检查敏感信息不会进入 DOM、URL、storage、日志、截图、trace 或 sourcemap。
5. 执行键盘、焦点、颜色对比、多视口和必要的截图回归。
